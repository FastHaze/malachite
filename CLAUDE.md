# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Malachite: an app for taking notes in a vault of Markdown files, written in Rust and open source. It is one of the successors to Obsidian: it works on the same kind of vault and keeps what people bring from there (`[[wikilinks]]`, `#tags`, properties, callouts, the three views of a note, the command names and hotkeys), and that is the reference for a design question. This paragraph and `README.md` are the only places that say so: the README, for people deciding whether to use Malachite, says that it works on vaults of `.md` files and is highly inspired by Obsidian, and that it is not affiliated with it. The code and its comments, the tests, the interface and `vault/Overview.md` do not name Obsidian or link to it: describe what Malachite does in its own terms. The one exception is the theme called Obsidian, asked for by that name: it is named and described as the stone, black volcanic glass, as the app is named for a stone itself, and it is the colours the app had before it had themes.

One crate with a library, the app itself (an egui GUI, the binary `malachite`) and a command-line binary (`malachite-cli`). The package is called `malachite-notes`, because `malachite` on crates.io is another project; the library (`[lib] name`) and the two programs keep the short name, so the code says `malachite::`. Math, Mermaid diagrams, pictures from the web, and embedded PDF, audio and video are deliberately not supported.

`vault/` is the default vault both binaries open (relative to the working directory). `vault/Overview.md` is the user-facing tour of every supported Markdown construct and shortcut — keep it in step when adding or changing a feature.

## Commands

```bash
cargo build                         # both binaries
cargo run --bin malachite-cli -- list # CLI; `--vault <dir>` (default: vault)
cargo run --bin malachite             # the app; optional first argument is the vault dir, else the vault open last time, else ./vault, else ~/Documents/Malachite
cargo run --bin malachite -- --graph  # start on the graph view (handy for looking at layout changes)
cargo test                          # everything
cargo test --lib                    # library only (vault, markdown, highlight, editing)
cargo test --bin malachite            # windowless GUI tests
cargo test --lib markdown::tests::lines_are_classified   # a single test
cargo test --bin malachite <name>     # a single GUI test
```

`dist/` holds copied release builds (`malachite.exe`, `malachite-cli.exe`), kept at hand through a `cargo clean`; they are not build output and not in the repository. Refresh them by hand from `target/release/` if needed. Started from there, the app opens the vault it had open last, not `./vault`, which is relative to the working directory.

### Toolchain constraint

The toolchain is Rust 1.83 (`rust-version` in `Cargo.toml`, and what CI builds with). Dependency versions in `Cargo.toml` are held back to ones that build on it, and `Cargo.lock` additionally pins `image`, `idna_adapter`, `webbrowser`, `home` and `unicode-segmentation`, and for Linux `jobserver`, `smithay-clipboard`, `wayland-protocols` and `indexmap`. Do not run a blanket `cargo update`; when adding a dependency, check that it and its transitive requirements build on 1.83, for Linux and macOS too, which a Windows build never reads: `cargo check --bins --tests --target x86_64-unknown-linux-gnu` (and `aarch64-apple-darwin`) finds a crate that is too new, and `cargo +<newer> update -p <crate> --precise <version>` pins it back. eframe itself is built from a changed copy in `vendor/eframe/` (below).

## Architecture

### Library (`src/`) — no GUI dependencies in the logic

- `lib.rs` — `Vault` (a root folder) and `Note`. All file operations: create (auto-numbered `Untitled`), rename (rewrites `[[links]]` in other notes, or with `relink` false leaves them; `linking` counts the notes it would rewrite), move between folders (a note with `move_note`, a folder with `move_folder`, which refuses to go into itself or onto a namesake), delete (`discard_at`/`discard_folder`: to `<vault>/.trash`, to the system's bin, or for good, as `Discard` says), daily note (`daily_in`: named for today in a Moment.js format, `YYYY-MM-DD` by default, found anywhere by that name or else made in a folder; `daily_neighbour` for the one before or after), plus `wikilinks()`, `tags()` and `aliases()` extraction. Notes resolve by file stem across the whole vault, so new titles are unique vault-wide; the `*_at(path)` variants exist to pick the right one of two namesakes. A name that is no note's title resolves to the first note listing it under `aliases` in its frontmatter: `resolve()` is the one place that decides this, so use it (or `Note::is_called`) rather than comparing titles. Folder paths are relative to the vault root, with the empty path meaning the top level, and must never escape the vault.
- `recycle.rs` — the system's bin: on Windows the Recycle Bin, reached with the shell's own file operation (`SHFileOperationW`, an `unsafe` call declared by hand as `window.rs`'s is). Elsewhere there is none yet, and `SYSTEM_BIN` says so. Only checked by hand: a test would fill the bin of whoever runs it.
- `lib.rs` also decides what an embed names: `is_attachment` and `is_picture` go by the file extension, so `![[Version 1.2]]` is a note. An embedded note counts as a link to it (`wikilinks`).
- `markdown.rs` — the line-oriented model everything else renders from. `parse()` gives each source line a `Kind` (heading, list item, quote, callout, code, table, …) and `inline()` splits text into `Span`s that are either content or *syntax markers*. A note link is `Link::Note(title, place)`, where the `Place` is the `#Heading` or `#^block` after the title, if any. **All ranges are byte offsets into the source**, and spans cover the content without gaps. `lib.rs` uses this same parser for tags and wikilinks, which is why code blocks and inline code yield neither.
- `outline.rs` — the structure of one note, read from `markdown::parse`: `headings()` for the outline pane, `find()` for the line a `Place` names, and `folds()` for what can be folded (a heading with text under it, a list item with deeper-indented lines under it) and the byte range each fold hides.
- `template.rs` — `fill()` puts `{{title}}`, `{{date}}` and `{{time}}` into a template's text, with Moment.js format letters translated for chrono; `formatted` and `read_date` write a date in such a format and read one back, which is how daily notes are named and found. Templates are the notes in a folder, `template::FOLDER` (`Templates`) unless the settings say another (`Vault::is_template` takes the folder).
- `graph.rs` — the vault as a graph (`Graph::build`: notes are nodes, resolved wikilinks are edges) and its 3D force layout (`Graph::layout`, deterministic, O(n²) with a pair budget so large vaults get fewer ticks).
- `search.rs` — the search query language (`Query::parse`, `matches`, `lines`) and `occurrences` for find-in-note. Parsing never fails: half-typed syntax matches as if it were not there, because the GUI searches on every keystroke. No regex support. Used by the CLI's `search`, the sidebar search and the find bar.
- `highlight.rs` — code-block tokenizer: `highlight(language, code)` returns `(range, Token)` pairs, where `Token` is a small set of roles the theme colours. Most languages are a `Syntax` table fed to one `generic` lexer (new C-like languages are a `const` using `..C_LIKE`); markup, CSS, YAML/TOML and diff have their own lexers. Approximate by design.
- `editing.rs` — pure text transforms for typing aids and editing commands (marker toggles, list continuation, indent, task toggle, headings, line moves, link and block inserts, bracket auto-pairing, and Ctrl+Backspace / Ctrl+Delete by words of any script, which egui's own text field takes to be Latin letters only, so that in Cyrillic it deleted back across lines to the last Latin letter or the start of the note). Each takes text + selection and returns an `Edit`, or `None` to let the key do its default.

### eframe (`vendor/eframe/`)

The app is built with a copy of eframe 0.31.1 (`[patch.crates-io]` in `Cargo.toml`), changed in one way: a frame that would draw exactly what the window already shows is not drawn (`src/native/shown.rs`; every changed place in `glow_integration.rs` is marked "Malachite's change", and `vendor/README.md` lists them). egui runs a frame for every move of the mouse, and eframe drew and presented the whole window for each, at the screen's refresh rate: 14% of a laptop's integrated graphics and a third of a processor core while the mouse merely moved over a note. Things to know:
- The frame is still run, as that is how egui finds out whether anything changed. Its shapes are compared with the last frame drawn, along with the window's size, scale and background colour; a frame that changes a texture, or is asked for a screenshot or the clipboard, is always drawn. A frame not drawn waits out the rest of the screen's refresh interval itself (`Shown::pace`), as a drawn one waits when it is presented; without that, frames ran as fast as the mouse reported moves.
- So drawing code needs to know nothing of this, as long as everything it shows is in its shapes and textures.
- Whatever can make the window lose what it shows has to make the next frame be drawn (`Shown::forget`): a new surface, a new size (which being minimised and restored is), a new scale, being covered or uncovered. And while frames run, one is drawn at least once a second whatever it holds.
- The windowless tests do not go through eframe and cannot see any of this. It was checked on a private copy of the app with a strip of its window on the screen: Windows stops updating the picture of a window wholly off the screen and holds its frames to about 23 a second, so neither pictures nor GPU figures taken of such a window can be trusted.
- Another version of eframe means making the change again on a fresh copy (`vendor/README.md`).

### Icon (`build.rs`, `assets/`)

`assets/malachite-icon.svg` is the one place the icon is kept, and `build.rs` makes both of its forms from it at build time, with no library: the window's picture (`icon.rgba` in `OUT_DIR`, which `main.rs` takes in with `include_bytes!` and gives the window), and on the MSVC toolchain the program file's own icon, written by hand as a compiled resource (`icon.res`, eight sizes) and handed to the linker for the `malachite` binary only. `build.rs` reads `<polygon>`s with a `#RRGGBB` fill and an `opacity`, which is all the drawing is made of, and stops the build on any other drawing element: redraw with polygons, or teach it more. `assets/malachite-icon.png` is a picture of the same drawing for use elsewhere; the app does not read it.

### CLI (`src/bin/malachite-cli.rs`)

A thin clap wrapper over `Vault`; no logic of its own.

### GUI (`src/bin/malachite/`)

- `main.rs` owns `App` (all state) and what can be done to a note. Drawing code never mutates state directly: it collects `Action`s during the frame, and `App::apply` runs them afterwards, so the note list is never modified while iterated. New behaviour usually means a new `Action` variant.
- `commands.rs` is the one table of things the keyboard can ask for (`COMMANDS`), with the command ids, names and default hotkeys these commands commonly have. A command is either `Run::Edit` (a pure function from `malachite::editing`, run by the editor on its selection) or `Run::App`. Add a hotkey or a palette entry there, not with a `consume_key` call. Hotkeys match their modifiers exactly, because AltGr arrives as Ctrl+Alt. App hotkeys run at the start of the frame; editing ones in `editor.rs::typing_keys`, only while the editor has the keyboard.
- `find.rs` is the find/replace bar, and the bar the same key brings up in the graph (below). It only computes where the matches are (`App::marks`) and asks the editor to go to one (`App::jump`); `editor.rs` selects and scrolls to a jump, and `live.rs` paints the marks under the text. The sidebar search uses the same `jump` when a found line is clicked, and so do the outline pane and links to a heading or block, with an empty range: that puts the caret there and scrolls the line to the top, where a match is centred. Reading view has no caret: find switches to the editing view, and a jump there only scrolls (`reading::show`'s `goto`).
- Sidebar search results are cached in `App::results` against `App::version`, which must be bumped wherever `App::notes` changes (`reload`, `save`, `open_vault`).
- **Nothing is parsed per frame.** A frame is drawn for every mouse move, so anything read out of notes is kept until its source changes (`cache.rs`): `App::index()` holds what comes from the whole vault (the names links can resolve to, each note's links for backlinks) against `App::version`, and `App::digest()` what the side panel and status bar show of the open note (headings, links, tags, aliases, counts) against the buffer's text (`App::digest_of` is the same for the note the graph has in focus). The editor's layout is kept the same way by `live::build_kept`, whose key is everything `live::build` reads. New drawing code should take from these rather than call `wikilinks()`, `tags()` or `outline::headings()` itself, and anything new that `live::build` comes to depend on has to join that key.
- `graph.rs` (GUI) is the graph view, Ctrl+G, shown in place of the editor while `App::show_graph`. It is a port of the 3D graph on aicodingdictionary.com, reverse engineered from that site's scripts: the constants (drift, springs, fades, camera framing, spin-in, focus distance) are the site's, and comments mark where this app departs from it. There are no shaders: every node and edge sample is projected by `Lens` and drawn with egui's painter in back-to-front layers. Things to know before changing it:
  - It is drawn at a pace (`GraphView::frames_per_second`): 60 a second while it is used and for `SETTLE` seconds after (the opening spin, a flight to a note, coasting), 30 while it only drifts, 15 while the window is behind another, and not at all at rest. `REST` seconds after the last input it slows to a stop over `EASE_TO_REST` and asks for no more frames until the mouse or keyboard does something; the site drifts for ever, which here kept the GPU busy for as long as the graph was on screen. So the drift runs on the graph's own clock (`drifted`, at `speed()`), not the time of day, or it would jump when it starts again; anything new that moves continuously has to go by `speed()` too, and anything that moves in answer to input has to keep the pace up (`stirred`, `busy`). A frame asked for with a delay makes egui's `stable_dt` a guess of one sixtieth of a second, so the graph measures its own time between frames (`drawn_at`). Keep per-frame work proportional to nodes + edges. A name's rim is drawn only over a disc, being the name drawn eight times.
  - Names are laid out at one of a few sizes (`laid_out_at`) and then stretched to their exact size (`stretched`), so that they grow evenly with the zoom: egui keeps a glyph set per distinct size, and text set at whole sizes jumped a point at a time. The stretch is worked out from what the glyphs measure, not from the size asked for, and separately for width and height, because egui makes glyphs at whole pixels and sets each letter a whole pixel after the last. Do not give the names sizes of their own again.
  - The view is kept (`App::graph`) while hidden and rebuilt only when `App::version` changes and the notes or links really differ; `GraphView::build` carries the camera and focus over.
  - A note in focus is shown with its neighbours alone, gathered as a search's notes are (below): `GraphView::choose` decides what is drawn, the note in focus and its neighbours, else what a search found and theirs, else everything, and `focus` gathers at once where a search waits. The camera then looks at the note where it has been gathered to, from where it already is.
  - Ctrl+F in the graph looks for a note by its name (`find.rs`: `GraphFind`, `App::graph_find_bar`), since there is no text there to look through; the command is the same one (`editor:open-search`) and decides by `App::show_graph`. While the bar is up the graph draws only what it has found and the notes linked with those (`GraphView::search`, called every frame, acting only on a change), as the site does, except that the site draws no neighbours, its search reading every word of a note and so mostly finding them anyway: the others shrink away and cannot be pointed at, only the links among the notes found are drawn, straight, and the fades and fog give way. A quarter of a second after the last change the notes drawn are gathered about the middle (`Graph::gather`, a small run of the site's forces on them alone) and the camera frames them; a note is gathered to by the same spring a neighbour leans on, and in focus it is looked at where it has been gathered to. Typing gives nothing the focus, and starting a search, or one that no longer finds the note in focus, lets go of it; Enter goes to the notes found in turn, and the bar says which note to go to and `graph_view` gives it the focus (`GraphView::focus`), fog or no fog, so the side panel follows as it does a click. A click on nothing while a note is in focus puts the bar away (`Outcome::StopSearching`). Names are matched by how they start and then by what is in them (`picker::rank`, without its loosest kind), at most the site's fifteen, and the notes found are kept against the name and `App::version`, because the graph draws every frame. The keys are in order: Enter and Esc are the bar's while its field has the keyboard, and the bar eats the Esc that closes it, or the graph would let go of its note for the same press. The bar is forgotten when the graph is put away.
  - The right-hand panel is about the note in focus while the graph is showing (`App::graph_focus`), and about the open note otherwise. It is drawn before the graph, so it follows a click one frame later, which nobody sees in a view that repaints every frame. The open note is still read from the buffer; any other from its saved text, with a digest of its own (`App::digest_of`), because the status bar goes on asking for the open note's. A click in the panel has to work from behind the graph: a heading opens its note first (the graph throws away a `jump`), and a link to a note that does not exist makes it beside the note in focus (`Action::NewNamed`), not beside the open one. A link or backlink to a note that does exist opens nothing while the graph is showing: it puts that note in focus there (`Action::Look`, taken up by `graph_view` on the next frame as the find bar's note is), so that a note is only opened by a click on it in the graph.
  - Fog (`FOG_FROM`/`FOG_TO`, as parts of the ball's radius behind its middle) fades out the far half, so only the nearer notes are drawn; the active note and its neighbours are lifted out of it, and a fogged note cannot be picked. The site has almost none.
  - Which note the mouse is on (`GraphView::pick`) is not simply the nearest one. A note's neighbours lean towards it while it is the active one, so what is under the pointer changes with what the pointer is on, and going by the nearest note each frame made a pointer held still between two linked notes, one behind the other, go back and forth between them several times a second. So: a pointer that has not moved stays with its note for as long as it is within reach of it, whatever comes under it; a moving one goes over to a disc in front of its note's (in front by where the notes rest, which hovering does not change), or to any disc once it is off its note's own; and the note the mouse is on stands still where it is (`animate`), where it used to go back to its place, out from under the pointer. Anything new that moves notes in answer to the mouse has to be looked at for the same loop.
  - Names that would overlap give way to the more important one (`Name::rank`); the site draws them all. A name is the discs' colour, so it is written over a rim of the page's colour that cuts it out of any disc under it.
  - The layout forces in `src/graph.rs` start from the site's but are rebalanced for vaults, where a few groups are densely linked and most notes are not: links pull less per link, linked notes repel each other more, unlinked ones less, and a minimum clearance is enforced at the end. Check any change against a real vault with `--graph`.
  - The look can only be judged by eye. `tests.rs` checks behaviour (picking, focus, drag, rebuild), not appearance. The tests in `graph.rs` itself can set notes where they want them and draw real frames with the mouse held at a place (`one_behind_another`, `watch`): that is how what the mouse is on, frame after frame, is tested.
- **Embeds and footnotes** (`embed.rs`, `reading.rs`, `live.rs`). `Link::Embed` is a picture or a note shown in place, `Link::Footnote` a footnote's mark and `Kind::Footnote` the line that defines one. Things to know before changing them:
  - Pictures are local files only, found by `Vault::attachment` (by path, or by name anywhere in the vault, never outside it or in a hidden folder). They are decoded once into textures in `App::pictures` and looked at again, by modification time, when `App::version` changes. The formats are the `image` features in `Cargo.toml`: WebP is not among them because `image-webp` could not be resolved on this toolchain.
  - Reading view draws an embedded note with the same `Reader`, one level deeper, up to `DEPTH`; that limit is what stops notes that embed each other. A checkbox inside an embedded note is not clickable: its range is in another note's text.
  - Live Preview only shows an embed that is alone on its line (`markdown::lone_embed`), and has to make room for it out of the line's own characters: one of them is given a `line_height` as tall as the embed, and the editor draws the picture or the note over that row (`Preview::embeds`). An embedded note's height is not known until it has been drawn, so it is measured each frame into `App::embed_heights` and the layout is rebuilt when it changes; `live::Blocks` carries those sizes and is part of `build_kept`'s key.
  - The editor draws its own caret (`editor.rs::caret_rect`); the text field is shown with a caret of no width. A text field's caret runs the whole height of its row and 1.5 points past each end, which on the row of an embed is down the embed and out under it. The selection the field draws down that row is painted over, to the row's exact bottom: anything further would cut into the line below.
  - An embed in the middle of a sentence is left as a link in Live Preview. Reading view breaks the line around it.
- **Coloured highlights.** Markdown has the one highlight, `==text==`, shown in yellow, and no way to name another colour. HTML in a note is shown, so a colour is written as `<mark style="background: #RRGGBBAA;">text</mark>`, which `markdown.rs` reads into `Style::tint` (hex colours only) and `editing::set_highlight` writes. The note's right-click menu (`editor.rs::highlight_menu`) offers them: the highlight yellow and six more presets, then a custom colour. egui moves the caret on a press of any mouse button, so the editor puts the selection back after a right click. The last custom colour is `highlight` in the settings file.
- `picker.rs` is the command palette (Ctrl+P), quick switcher (Ctrl+O), vault switcher and template list, one modal over four lists. Picking a template sets `App::pending_insert`, which the editor puts in at the caret the way it runs a `pending_edit`. egui lays a dialog out in the room it took the last time it was drawn, closed in between or not, so anything in a dialog that takes what room there is (a scroll area) can only shrink: the list is given room of its own (`allocate_ui`), or one search that narrowed it to a row would leave every list after it three rows high.
- **Switching vaults** is `App::open_vault`: it saves, reads the other vault completely, and only then replaces the state, so a vault that cannot be read leaves the app where it was. Per-vault state (open note, history, folds, filter, and the vault's own settings file, written first if changed) is reset there; add any new per-vault field to that list. Folded folders are the exception: they are kept for each remembered vault (`App::folded_elsewhere`, and `folded` lines under the vault's `recent` line in `settings.txt`) and taken up again after the note is shown (`take_up_folded`), so the list comes back as it was left even if that hides the open note. Remembered vaults are `recent` lines in the settings file. The folder dialog (`rfd`) is a Windows/macOS-only dependency; elsewhere a vault is opened by typing its path. The dialog is the system's: it is on the real screen, the app stands still until a person answers it, and it is given the app's window to belong to so that it cannot end up behind it. For those reasons it is only ever brought up by `eframe::App::update`, from the flag `App::browse` that `Action::BrowseVault` sets: tests draw frames with `App::ui` and so cannot reach it, and nothing else may call `picker::choose_folder`.
- **Settings** are three files, and they are different kinds of thing. `settings.txt` (`settings.rs`) is what the app remembers of how it was left: zoom, panels, the last vault, the folders left folded in each vault. It is the app's, rewritten whole. Beside it in the user's settings folder, `malachite.conf` is what the user has chosen for the app, which is how it looks; and in each vault, `.malachite/malachite.conf` (`files::VAULT_FILE`) is what the user has chosen for that vault, which is its notes as files. Those two are the user's: files to edit by hand, in the format of `conf.rs` (`[section]`, `name = value`, `#` comments, no comments at the end of a line because a colour is `#rrggbb`). Things to know before adding a setting:
  - The app has had other names (`notes-gui`, `smaragd`), and `settings::inherit` takes over the settings folder of the latest of them the first time it starts under this one. `main()` calls it, and only when the settings are where they are by default. The app does this itself because nothing else is sure to see the same folders: a program started from inside a packaged app (this assistant's sessions among them) is shown a private copy of `%APPDATA%`, and what it writes there the user's own run of the app never sees.
  - Each file is a `settings_dialog::ConfFile` (`App::conf`, `App::vault_conf`): where it is, its text, whether that is yet to be written, and its problems. `appearance.rs` reads the app's: `[appearance]` (theme, scheme, text size, line width) and `[colors.dark]` / `[colors.light]`, whose colours are the `PAINTS` table. `files.rs` reads a vault's: `[files]` (where new notes start, whether a rename updates links, where deleted notes go, the templates folder, the daily note's folder, format and template). Each says of a section that belongs in the other file that it does. `App::set_option` writes a setting into the file its section belongs to. A new setting is a field of `Appearance` or `Files`, an arm of its `option`, a line of its `template()` and a row of the dialog. Reading never fails: a line that is not understood is skipped and reported, by its number and its file.
  - Which file a setting goes in is whether it means the same in every vault. `[files]` names a vault's folders, so it is the vault's; a look is the app's. A vault's file is not written until one of its settings is changed, so opening a vault leaves nothing in it. A setting's default is what the app did before it was one (new notes beside the open one, links always updated, deletions to `.trash`).
  - **Themes** are `appearance::Palette`: Gem (the default: the greens of the icon, with the colours the user had picked by hand for accent and highlight), Obsidian and Aperture. A theme is two rows of colours, light scheme and dark, in the order of `PAINTS`, and nothing else (`GEM`, `OBSIDIAN`, `APERTURE`). A new theme is a variant, its two rows, its word, name and line of description, and a place in `Palette::ALL`; the dialog draws a picture of each from its rows. A new colour is a row of `PAINTS`, a constant for its place, and a value in every theme's two rows. A colour the file sets in `[colors.*]` holds in any theme, which is why the dialog says so under the themes and offers to put them back.
  - A colour that lets what is behind it through (the highlight) does not come out as plain blending would have it: egui multiplies such a colour out in linear light, so it shows brighter and yellower than its digits suggest. Choose one by what it shows as on the page, not by arithmetic.
  - The app only ever rewrites the one line of a setting (`conf::set`, `conf::unset`), so comments and order in the file are kept. A setting put back to its default becomes a comment again, and the file as first written is `template()`: every setting, commented out, under a line that says what it is.
  - What a colour is when left alone depends on the theme, so the commented lines have to follow it: `appearance::in_step` rewrites those that show some theme's colour to show the current theme's (`conf::recomment`), and the line that names whose they are. It also brings a file from before there were themes up to date, where light or dark was said as `theme`, which is `scheme` now. It changes nothing the file says, and is run on the text wherever it comes in or is changed (`App::new`, `reload_conf`, `set_option`); if that changed anything, the file is written back.
  - `settings_dialog.rs` is the dialog (Ctrl+,). It keeps no state of its own but which page it is on (`Page`, in egui's memory): a change is `App::set_option`, which rewrites the line in its file's text, reads the texts again into `App::look` and `App::files` and sets `App::restyle`. The files are written when the mouse is let go, and read again when the window gets the focus back (each unless it has a change of its own not yet written), so the dialog and a text editor are two ways of doing the same thing. A new page of the dialog is a variant of `Page`, a method drawing it, and the file its footer offers to open. The dialog moves into place over its first frames, so a test waits before clicking in it.
  - `Theme::of(&look, dark, faces)` is the look to draw a note in, and `App::theme(ctx)` is how drawing code gets it; `theme::apply` is the part of it the interface around the note takes (panel fill, selection, links), and has to be called again when the look changes, which `restyle` sees to. `Theme::key` tells one look from another and is part of `live::build_kept`'s key.
  - A theme has no colours for the interface's own widgets (buttons, fields, menus, dialogs). `theme::apply` makes them out of the theme's panel and text colours, each some part of the way from one to the other, with the parts chosen so that a grey theme gets the greys egui gives such things anyway (a test holds it to that); a theme of another colour then has its colour in everything. Fonts are not settings yet: `theme::install` loads a sans-serif every system of its kind has, with real bold and italic faces (`face_files`: Segoe UI on Windows, Arial on macOS, DejaVu Sans or Noto Sans on Linux), and falls back to egui's own font, slanted and brightened, where there is none.
- **The window has no title bar** (`window.rs`; `with_decorations(false)` in `main()`), so what a title bar does is the app's to do. Things to know before changing the top of any panel:
  - The top row of each panel is a bar the window is moved by (`window::title_bar`): the tools above the note list, the bar above the note (`header`), the top of the right-hand panel. `title_bar` has to be called before the row's buttons are added, because the widget added last gets the mouse; it also puts the row at one height in every panel. A drag there is `ViewportCommand::StartDrag` and a double click maximises: the move itself is the system's, which is what keeps snapping to the screen's sides working. A label in such a row must not be selectable, or it takes the drag.
  - The three window buttons (`App::window_buttons`) are flush against the top right corner, out through the panel's margins, and beside them is the toggle of the right-hand panel (`App::corner`). The right-hand panel draws them while it is showing and `header` while it is not (`App::info_showing`), at the same place on the screen; so `header` is drawn even with no note open, with less in it, or there would be no way to move or close the window.
  - Resizing is by the edges, and the app has to say when: a press of the mouse within a few points of an edge is taken out of the input before egui sees it (`App::take_edge_press`, from `raw_input_hook`) and becomes `ViewportCommand::BeginResize`, so that nothing drawn at the edge is pressed as well. A maximised window has no edges to hold, and there the close button reaches the corner.
  - A window without a title bar is a bare rectangle to Windows: no round corners, no line round it. `window::dress` asks for them (`DwmSetWindowAttribute`, one of the app's two `unsafe` calls, the other being `recycle.rs`'s, and why `raw-window-handle` is a dependency on Windows). What the system draws round a window is not in a picture taken of the window: it can only be checked on the screen.
  - Tests see all of this as what the app asks of its window (`TempApp::asks`, the `ViewportCommand`s a frame gives back), and find the buttons that are pictures in `App::spots`. Nothing there moves a real window: dragging and resizing with a real mouse have to be tried by hand.
- **One Enter, one thing.** A button that has the keyboard is pressed with Enter, and what it opens is drawn later in that same frame with the key still down. So a dialog or list does not take Enter in the frame it comes up in (`Picker::fresh`, `under_modal` in `confirm_dialog`, which asks before deleting and, when the settings say to, before a rename updates links): otherwise the Delete button deletes without asking, and the vault's name in the status bar goes straight to the first row of its list.
- **Focus after a modal**: egui refuses the keyboard to widgets under a modal until the frame after it was last drawn, and lays a new modal out for one invisible, disabled frame. So `App::focus` and `pending_edit` are held for a frame after a dialog closes (`under_modal`), and the picker asks for the keyboard twice. Keep this in mind for any new dialog.
- Three views of a note: Live Preview and Source mode are both the editor in `live.rs`; Reading view is `reading.rs`. `editor.rs` picks between them.
- **Live Preview trick** (`live.rs`): egui's `TextEdit` draws exactly the buffer's characters, so syntax cannot be removed. Instead hidden markers are laid out at a font size too small to take any width, and markers that are replaced with a drawing (bullets, checkboxes, quote bars, rules) stay in place but transparent with the drawing painted over them. Markers reappear when the cursor touches their construct.
- **Folding** is the same trick applied to whole lines: what a closed fold hides, line breaks included, is one section in the hidden format, and egui rounds its rows to no height. Things to know before changing it:
  - The text is all still in the buffer, so the caret can walk into a fold. It is not kept out; instead a fold opens as soon as the selection or a `jump` touches what it hides (`unfold_around`), and folding moves a caret that is inside to the end of the line left showing (`leave_folds`, through `App::caret`). Skipping the caret over a fold would be the more usual way.
  - Folds are kept in `App::folds` per note file as the *text of the folded line*, not as an offset, so edits elsewhere need no bookkeeping. Rewording a folded line opens it, and two identical lines fold together. They are not saved between runs.
  - `live::build` works the folds out from the text it is given, never from `App::buffer`: inside the text field's layouter the two can differ by a keystroke, and byte ranges from the wrong one would split a character.
  - The arrows are drawn and clicked in `editor.rs` (`Preview::arrows` says where), only for folded lines and the line under the mouse, so a long list does not cost a widget per item. Reading view does not fold.
- `panels.rs` draws everything around the note (the right panel is the outline first, then links, backlinks and tags), `tree.rs` the folder/note tree (and drag-to-move, of notes and folders alike, as one payload, `tree::Dragged`; a folder's row shows its count of notes, worked out by `folders::arrange` into `Row::Folder`, not per frame; its row icons are painted stroke by stroke in `paint_icon`, as there is no icon font, and the tools above the list are the same pictures as buttons, `tree::tool`: new note, new folder, today, and a pair of chevrons of their own that folds every folder or unfolds them all, going by what the list shows, `App::all_folded`), `folders.rs` the folder operations and tree arrangement, `theme.rs` fonts and colours, `autoscroll.rs` middle-click autoscroll, `settings.rs` the remembered zoom/panels/mode as `key = value` lines in the user's settings folder.
- Back/forward history is two stacks of note paths on `App`. `show_note` records the note being left; `load_note` shows one without recording, which is what `travel` uses. Paths that no longer exist are skipped, so renames and deletions need no bookkeeping.
- Saving is automatic, `AUTOSAVE_DELAY` after the last keystroke; changes made on disk by other programs are picked up when the window regains focus.

### GUI tests (`src/bin/malachite/tests.rs`)

The whole interface is tested without a window: `TempApp` builds an `App` on a temp-dir vault (and when dropped removes the vault the app ends in, but only if it is a `malachite-test-…` folder in the system temp dir: an app can be led to another vault, and that one is not a test's to delete), draws frames into a bare `egui::Context`, and feeds simulated mouse/keyboard events via `frame_with`. `App` has several `#[cfg(test)]` fields that record what a frame drew so tests can assert on it. `App::new` takes the settings path as a parameter so tests never touch the real settings file. Library tests use the same pattern with `TempVault`.

## Releases

The repository is `github.com/FastHaze/malachite`, under the MIT licence (`LICENSE`). Versions are semantic, 0.x for now, and `version` in `Cargo.toml` is the one place the number is kept. `CHANGELOG.md` is in the Keep a Changelog form: add to `[Unreleased]` with a change people would notice. A release is: move `[Unreleased]` under a new version and date, bump `Cargo.toml` (and `Cargo.lock` with it, by building), commit, tag `vX.Y.Z` and push the tag. `.github/workflows/release.yml` then refuses a tag that is not the version in `Cargo.toml`, tests on each system, builds Windows (x64), Linux (x64, on the oldest runner for an older glibc) and macOS (one program for Apple silicon and Intel, in a `Malachite.app` made by hand and signed for the machine only, not by Apple), and publishes them with that version's part of the changelog as the notes. `ci.yml` builds and tests all three on each push. The windowless tests are the only ones run on macOS and Linux: what the window does there has not been seen.

## Conventions

- Every module opens with a `//!` comment explaining what it does and why; item comments explain intent in plain prose. Keep this style.
- Test names are sentences describing behaviour (`rename_refuses_to_overwrite`, `enter_on_an_empty_item_ends_the_list`).
- File operations must never overwrite an existing note or folder — conflicts are an error or get a numbered name.
